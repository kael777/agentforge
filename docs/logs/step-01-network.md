# Step 1：跨服务商 WireGuard 组网与服务器基线

> 日期：2026-10-29
> 环境：三台 Ubuntu 24.04 VPS，分属不同服务商，各有公网 IP，**没有共享内网**
> 结果：完成，外部扫描只剩 22，陌生来源不可达

## 为什么先做组网

三台机器不在同一家云，拿不到共享内网。直接后果是：任何服务间通信都得走公网。

原方案是给监控端口（Loki 写入、Prometheus remote write）开公网 + basic auth。
问题是**凭据在公网上是明文传输的**，而且每台机器都要单独维护另外两台的 IP。

所以第一步不是装软件，是造一张自己完全掌控的虚拟网。

## 为什么选 WireGuard 而不是 Tailscale

| | WireGuard | Tailscale |
|---|---|---|
| 控制面 | 自己配 | 第三方协调服务器（闭源） |
| 数据面 | 内核态 | WireGuard |
| 加机器 | 手改配置 | 登录即可 |
| 依赖 | 无 | 控制面不可用则新连接建不起来 |

选 WireGuard 的理由：这个项目要演示"运维基建"，每一层都该看得见。
密钥交换、AllowedIPs、握手、转发，出问题能一层层查下去，而不是被客户端藏起来。

代价是加机器要手改配置——但只有三台，而且星形拓扑下只需改 hub。

## 拓扑

```
        应用 A                应用 B
            \                  /
         UDP 51820（加密隧道）
                \            /
              基建中心（hub）
```

- hub: `<hub>`，唯一在公网监听 UDP 51820 的机器
- 应用 A: `<app-a>`
- 应用 B: `<app-b>`
- 开发机按需加入为 road warrior（`<dev>`）

星形而不是网状：只有 hub 需要一个稳定的公网入口，A 和 B 只要主动连出去。
加第四台机器时，只在 hub 追加一段 `[Peer]`，已有机器的配置一行不改。

## 执行步骤

1. **三台生成密钥**：`wg genkey` → private/public，私钥不出机器
2. **hub 配置**：`Address <hub>/24`、`ListenPort 51820`、两个 `[Peer]`（无 Endpoint）、`ip_forward=1`
3. **A/B 配置**：各自 `Address`、`Endpoint = <hub 公网 IP>:51820`、`AllowedIPs = 10.88.0.0/24`、`PersistentKeepalive = 25`
4. **安全组**：三台只加一条 UDP 51820，来源写死另外两台的公网 IP
5. **SSH 加固**：建 `deploy` 用户、禁密码登录、限制 `AllowUsers`
6. **防火墙**：`ufw` 默认拒绝，22 只对办公出口 IP 与 `10.88.0.0/24` 开放
7. **hub 额外**：放开 51820/udp，并允许 wg0 → wg0 的转发

## 关键点

**只有 hub 需要开 51820。** 防火墙是有状态的：A/B 主动连 hub，回包自动放行。
hub 是"被连接方"，那才是新入站连接，必须显式允许。

**两条规则管两件事。** `allow 51820/udp` 决定握手包能否到达；`ufw route allow in on wg0 out on wg0`
决定解开封装后能否转发给另一个 peer。后者不开，表现是"能通 hub，通不了另一个 spoke"。

**`AllowedIPs` 绝不能写 `0.0.0.0/0`。** 那会变成出口节点，把云主机的默认网关顶掉，SSH 当场断线。

**配置里的私钥用 `$(sudo cat ...)` 内联**，不是直接粘贴——避免私钥出现在命令历史和聊天记录里。

## 踩的坑

| 坑 | 现象 | 原因 |
|---|---|---|
| 握手一直不成功 | `latest handshake` 为空，`ping <hub>` 超时 | 安全组协议选成了 **TCP**，WireGuard 用的是 **UDP 51820** |

云控制台的协议下拉框默认是 TCP，选错就等于没开——但界面上看起来"端口已经放行了"。
用 `tcpdump -ni any udp port 51820` 判断：没有包进来，就是被挡在主机之外。

## 验收

| 项 | 结果 |
|---|---|
| 外部端口扫描（三台） | 只看到 22 |
| 陌生来源（手机热点）访问 22 | 全部超时 |
| `ufw status` | 22 的来源是具体 IP，不是 `Anywhere` |
| `ping <hub>` | 通，41 ms，0% 丢包 |
| `ping <app-b>`（A → B） | 通（经 hub 转发） |

## 41 ms 带来的一个发现

这个延迟说明 A 和基建不在同一区域。原计划假设"两台应用机同 VPC"，不成立。

于是 B 访问数据库的路径变成 `B → hub → A`，往返约 80 ms。一个请求查三次库就是 240 ms 纯等待。

处理方向（待定）：**A 对外服务，B 只做发布演练**——把流量集中在 A（数据库走回环），
B 用来演练切换和回滚，不承担日常流量。这样架构不变，只是 Nginx 不把 B 挂进 upstream。

## 遗留

- 开发机加入网络（road warrior）暂未配置
- 数据库尚未部署，`B → A:3306` 的连通性要等 Step 3 验证
- 41 ms 对日志推送可以接受，但 Loki 的批量与压缩参数要按这个延迟调
