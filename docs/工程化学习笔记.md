# AgentForge 工程化学习笔记

这份文档记录搭建 AgentForge 过程中遇到的工程化知识。重点不是记住配置，而是理解它解决什么问题、如何验证，以及出现问题时应该怎样排查。

## 记录方式

每个知识点尽量回答四个问题：

1. 我遇到了什么现象？
2. 这个机制解决什么问题？
3. AgentForge 如何配置？
4. 如何验证配置真的生效？

## 1. `.gitattributes`：统一跨平台文件格式

### 遇到的现象

在 Windows 上执行 `git diff --check` 时出现：

```text
warning: LF will be replaced by CRLF the next time Git touches it
```

这不是代码错误，而是 Git 提醒工作区文件的换行符可能被转换。

### LF 和 CRLF 是什么

- Linux 和 macOS 通常使用 LF（`\n`）换行。
- Windows 文本文件传统上使用 CRLF（`\r\n`）换行。
- Git 的 `core.autocrlf` 配置可能在仓库和 Windows 工作区之间自动转换换行符。

普通 Go 源码通常能兼容两种换行符，但 shell 脚本如果被保存为 CRLF，在 Linux 上可能出现下面的错误：

```text
/bin/bash^M: bad interpreter
```

### `.gitattributes` 的作用

`.gitattributes` 是仓库级规则。它告诉 Git 不同类型的文件应该怎样标准化，不依赖每位开发者电脑上的全局 Git 设置。

AgentForge 当前配置：

```gitattributes
* text=auto

*.go text eol=lf
go.mod text eol=lf
go.sum text eol=lf
*.sh text eol=lf
*.md text eol=lf
*.yml text eol=lf
*.yaml text eol=lf
Dockerfile text eol=lf
Makefile text eol=lf

*.bat text eol=crlf
*.cmd text eol=crlf
```

规则含义：

- `* text=auto`：让 Git 自动识别文本文件并在仓库中标准化。
- `eol=lf`：检出到工作区时也保持 LF，适合 Go、Linux 脚本、Docker 和 CI 配置。
- `eol=crlf`：Windows 批处理文件保持 CRLF。

### 如何验证

查看某个文件实际匹配到的属性：

```powershell
git check-attr text eol -- backend/gofiber-gorm-next/cmd/api/main.go
git check-attr text eol -- backend/gofiber-gorm-next/build.sh
git check-attr text eol -- backend/gofiber-gorm-next/build.bat
```

查看 Git 索引和工作区使用的换行符：

```powershell
git ls-files --eol
```

提交前检查空白和换行问题：

```powershell
git diff --check
git diff --cached --check
```

## 2. `secret-scan.yml`：在 CI 中检查密钥泄漏

### 为什么仅有 `.gitignore` 不够

`.gitignore` 只能阻止尚未被 Git 跟踪的文件进入后续提交。它不能：

- 删除已经提交到 Git 历史中的密钥；
- 阻止开发者把密钥写进其他源码或配置文件；
- 判断一段字符串是否像 API Key、Token 或私钥。

因此，`.env` 加入 `.gitignore` 是第一层保护，密钥扫描是另一层保护。

### Gitleaks 做什么

Gitleaks 根据规则检查仓库内容和 Git 历史中疑似存在的密码、Token、API Key、私钥等敏感信息。AgentForge 把它放在独立的 GitHub Actions 工作流中：

```text
.github/workflows/secret-scan.yml
```

核心配置：

```yaml
name: Secret Scan

on:
  push:
  pull_request:
  workflow_dispatch:

permissions:
  contents: read

jobs:
  gitleaks:
    name: Gitleaks
    runs-on: ubuntu-latest
    steps:
      - name: Checkout full history
        uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          fetch-depth: 0

      - name: Scan repository for secrets
        uses: gitleaks/gitleaks-action@e0c47f4f8be36e29cdc102c57e68cb5cbf0e8d1e # v3.0.0
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

### 配置逐项解释

- `push`：每次推送代码后扫描。
- `pull_request`：PR 合并前扫描。
- `workflow_dispatch`：允许在 GitHub Actions 页面手动运行。
- `contents: read`：遵循最小权限原则，扫描任务只读取仓库。
- `fetch-depth: 0`：检出完整历史，使扫描不局限于最新提交。
- `GITHUB_TOKEN`：由 GitHub Actions 自动生成，不需要手工创建或写进仓库。
- Action 使用完整 commit SHA：降低第三方标签被移动或篡改带来的供应链风险。

个人账号下的公开仓库使用当前 Gitleaks Action 不需要设置 `GITLEAKS_LICENSE`；如果以后把仓库转移到 GitHub Organization，需要重新检查官方许可要求。

### 和 GitHub Secret Scanning 的区别

- GitHub Secret Scanning / Push Protection 是 GitHub 平台提供的保护，可以在推送阶段识别受支持的密钥类型。
- Gitleaks 是仓库自己的 CI 检查，规则和运行结果作为项目流水线的一部分存在。

两者是互补关系，不需要二选一。

### 扫描失败时怎么办

处理顺序很重要：

1. 不要在 Issue、聊天或截图中继续传播完整密钥。
2. 如果是真实密钥，先在对应平台撤销或轮换。
3. 从当前代码中删除密钥，改为环境变量或密钥管理服务。
4. 检查密钥是否仍存在于 Git 历史；只删除最新文件并不等于安全。
5. 只有确认是假阳性后，才添加精确的忽略规则。

不要为了让 CI 变绿而直接忽略一个未经确认的告警。

## 3. Go module path：代码包的正式身份

### module path 是什么

`go.mod` 第一行定义当前 Go module 的唯一导入前缀。脚手架最初使用临时名称：

```go
module gofiber-gorm-next
```

仓库确定后改为与代码位置一致的正式路径：

```go
module github.com/kael777/agentforge/backend/gofiber-gorm-next
```

因此，内部包也从：

```go
import "gofiber-gorm-next/internal/config"
```

改为：

```go
import "github.com/kael777/agentforge/backend/gofiber-gorm-next/internal/config"
```

这样，模块身份、仓库地址和源码目录是一致的，也便于其他工具理解代码来源。

### PowerShell 参数的坑

下面这种写法在当前 PowerShell/Go 环境中被错误拆分：

```powershell
go mod edit -module=github.com/kael777/agentforge/backend/gofiber-gorm-next
```

表现为 Go 尝试打开 `.com/kael777/...`。稳定写法是把参数值单独加引号：

```powershell
go mod edit -module "github.com/kael777/agentforge/backend/gofiber-gorm-next"
```

或者把整个参数加引号：

```powershell
go mod edit "-module=github.com/kael777/agentforge/backend/gofiber-gorm-next"
```

这次经验说明：命令本身看似正确时，还要考虑 shell 如何把文本拆成参数。

### 修改后的验证顺序

```powershell
go fmt ./...
go mod tidy
go test ./...
go vet ./...
go build ./cmd/api ./cmd/migrate
```

将两个 `main` 包放在同一条 `go build` 命令中，只进行编译验证，不会在当前目录留下 `api.exe` 和 `migrate.exe`。

## 4. 当前形成的安全与质量防线

```text
本地编辑
  ├─ .gitignore：避免提交本地环境文件和构建产物
  ├─ .gitattributes：固定跨平台文本格式
  ├─ go fmt / test / vet / build：检查后端格式、测试和编译
  └─ git diff --check：检查空白和换行问题
       ↓
GitHub
  ├─ Push Protection：尽量在敏感信息进入仓库前阻止推送
  ├─ Secret Scan / Gitleaks：扫描提交和历史
  └─ AgentForge CI：检查后端、前端和 Compose 配置
```

这些机制不能保证永远不出错，但可以把很多依赖人工记忆的检查变成自动执行的规则。
