# AgentForge 工程化学习笔记

这份文档记录搭建 AgentForge 过程中遇到的工程化知识。重点不是记住配置，而是理解它解决什么问题、如何验证，以及出现问题时应该怎样排查。

## 记录方式

每个知识点尽量回答四个问题：

1. 我遇到了什么现象？
2. 这个机制解决什么问题？
3. AgentForge 如何配置？
4. 如何验证配置真的生效？

## 1. `.gitattributes`：统一跨平台文件格式

### 遇到的现象

在 Windows 上执行 `git diff --check` 时出现：

```text
warning: LF will be replaced by CRLF the next time Git touches it
```

这不是代码错误，而是 Git 提醒工作区文件的换行符可能被转换。

### LF 和 CRLF 是什么

- Linux 和 macOS 通常使用 LF（`\n`）换行。
- Windows 文本文件传统上使用 CRLF（`\r\n`）换行。
- Git 的 `core.autocrlf` 配置可能在仓库和 Windows 工作区之间自动转换换行符。

普通 Go 源码通常能兼容两种换行符，但 shell 脚本如果被保存为 CRLF，在 Linux 上可能出现下面的错误：

```text
/bin/bash^M: bad interpreter
```

### `.gitattributes` 的作用

`.gitattributes` 是仓库级规则。它告诉 Git 不同类型的文件应该怎样标准化，不依赖每位开发者电脑上的全局 Git 设置。

AgentForge 当前配置：

```gitattributes
* text=auto

*.go text eol=lf
go.mod text eol=lf
go.sum text eol=lf
*.sh text eol=lf
*.md text eol=lf
*.yml text eol=lf
*.yaml text eol=lf
Dockerfile text eol=lf
*.Dockerfile text eol=lf
Makefile text eol=lf

*.bat text eol=crlf
*.cmd text eol=crlf
```

规则含义：

- `* text=auto`：让 Git 自动识别文本文件并在仓库中标准化。
- `eol=lf`：检出到工作区时也保持 LF，适合 Go、Linux 脚本、Docker 和 CI 配置。
- `eol=crlf`：Windows 批处理文件保持 CRLF。

### 如何验证

查看某个文件实际匹配到的属性：

```powershell
git check-attr text eol -- backend/gofiber-gorm-next/cmd/api/main.go
git check-attr text eol -- backend/gofiber-gorm-next/build.sh
git check-attr text eol -- backend/gofiber-gorm-next/build.bat
```

查看 Git 索引和工作区使用的换行符：

```powershell
git ls-files --eol
```

提交前检查空白和换行问题：

```powershell
git diff --check
git diff --cached --check
```

## 2. `secret-scan.yml`：在 CI 中检查密钥泄漏

### 为什么仅有 `.gitignore` 不够

`.gitignore` 只能阻止尚未被 Git 跟踪的文件进入后续提交。它不能：

- 删除已经提交到 Git 历史中的密钥；
- 阻止开发者把密钥写进其他源码或配置文件；
- 判断一段字符串是否像 API Key、Token 或私钥。

因此，`.env` 加入 `.gitignore` 是第一层保护，密钥扫描是另一层保护。

### Gitleaks 做什么

Gitleaks 根据规则检查仓库内容和 Git 历史中疑似存在的密码、Token、API Key、私钥等敏感信息。AgentForge 把它放在独立的 GitHub Actions 工作流中：

```text
.github/workflows/secret-scan.yml
```

核心配置：

```yaml
name: Secret Scan

on:
  push:
  pull_request:
  workflow_dispatch:

permissions:
  contents: read

jobs:
  gitleaks:
    name: Gitleaks
    runs-on: ubuntu-latest
    steps:
      - name: Checkout full history
        uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          fetch-depth: 0

      - name: Scan repository for secrets
        uses: gitleaks/gitleaks-action@e0c47f4f8be36e29cdc102c57e68cb5cbf0e8d1e # v3.0.0
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

### 配置逐项解释

- `push`：每次推送代码后扫描。
- `pull_request`：PR 合并前扫描。
- `workflow_dispatch`：允许在 GitHub Actions 页面手动运行。
- `contents: read`：遵循最小权限原则，扫描任务只读取仓库。
- `fetch-depth: 0`：检出完整历史，使扫描不局限于最新提交。
- `GITHUB_TOKEN`：由 GitHub Actions 自动生成，不需要手工创建或写进仓库。
- Action 使用完整 commit SHA：降低第三方标签被移动或篡改带来的供应链风险。

个人账号下的公开仓库使用当前 Gitleaks Action 不需要设置 `GITLEAKS_LICENSE`；如果以后把仓库转移到 GitHub Organization，需要重新检查官方许可要求。

### 和 GitHub Secret Scanning 的区别

- GitHub Secret Scanning / Push Protection 是 GitHub 平台提供的保护，可以在推送阶段识别受支持的密钥类型。
- Gitleaks 是仓库自己的 CI 检查，规则和运行结果作为项目流水线的一部分存在。

两者是互补关系，不需要二选一。

### 扫描失败时怎么办

处理顺序很重要：

1. 不要在 Issue、聊天或截图中继续传播完整密钥。
2. 如果是真实密钥，先在对应平台撤销或轮换。
3. 从当前代码中删除密钥，改为环境变量或密钥管理服务。
4. 检查密钥是否仍存在于 Git 历史；只删除最新文件并不等于安全。
5. 只有确认是假阳性后，才添加精确的忽略规则。

不要为了让 CI 变绿而直接忽略一个未经确认的告警。

## 3. Go module path：代码包的正式身份

### module path 是什么

`go.mod` 第一行定义当前 Go module 的唯一导入前缀。脚手架最初使用临时名称：

```go
module gofiber-gorm-next
```

仓库确定后改为与代码位置一致的正式路径：

```go
module github.com/kael777/agentforge/backend/gofiber-gorm-next
```

因此，内部包也从：

```go
import "gofiber-gorm-next/internal/config"
```

改为：

```go
import "github.com/kael777/agentforge/backend/gofiber-gorm-next/internal/config"
```

这样，模块身份、仓库地址和源码目录是一致的，也便于其他工具理解代码来源。

### PowerShell 参数的坑

下面这种写法在当前 PowerShell/Go 环境中被错误拆分：

```powershell
go mod edit -module=github.com/kael777/agentforge/backend/gofiber-gorm-next
```

表现为 Go 尝试打开 `.com/kael777/...`。稳定写法是把参数值单独加引号：

```powershell
go mod edit -module "github.com/kael777/agentforge/backend/gofiber-gorm-next"
```

或者把整个参数加引号：

```powershell
go mod edit "-module=github.com/kael777/agentforge/backend/gofiber-gorm-next"
```

这次经验说明：命令本身看似正确时，还要考虑 shell 如何把文本拆成参数。

### 修改后的验证顺序

```powershell
go fmt ./...
go mod tidy
go test ./...
go vet ./...
go build ./cmd/api ./cmd/migrate
```

将两个 `main` 包放在同一条 `go build` 命令中，只进行编译验证，不会在当前目录留下 `api.exe` 和 `migrate.exe`。

## 4. README 状态徽章：把流水线结果展示出来

### 状态徽章是什么

状态徽章（status badge）是 README 中的一张动态 SVG 图片。GitHub 根据某个 Actions 工作流最近一次符合条件的运行结果生成它，常见状态包括 `passing`、`failing` 和 `no status`。

徽章不会执行 CI，也不会阻止不合格代码合并；它只是把流水线状态展示给访问仓库的人。真正的质量门禁仍然来自工作流本身以及仓库的分支保护规则。

### Markdown 结构

一个可点击的徽章实际由“链接里面嵌套图片”组成：

```markdown
[![显示文字](徽章图片地址)](点击后打开的地址)
```

AgentForge 使用两个徽章：

```markdown
[![AgentForge CI](https://github.com/kael777/agentforge/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/kael777/agentforge/actions/workflows/ci.yml)
[![Secret Scan](https://github.com/kael777/agentforge/actions/workflows/secret-scan.yml/badge.svg?branch=main)](https://github.com/kael777/agentforge/actions/workflows/secret-scan.yml)
```

以第一个徽章为例：

- `![AgentForge CI](...)`：在 README 中显示一张图片，`AgentForge CI` 是图片无法加载时的替代文字。
- `actions/workflows/ci.yml/badge.svg`：根据 `.github/workflows/ci.yml` 生成状态图片。
- `?branch=main`：只显示 `main` 分支对应的状态，不让功能分支的临时结果干扰仓库首页。
- 最外层链接：点击徽章后进入该工作流页面查看运行记录和日志。

GitHub 默认展示默认分支的状态，也支持通过 `branch` 和 `event` 查询参数限定分支或触发事件。这里显式写出 `branch=main`，让读者一眼能看懂徽章代表什么。

### 如何从 GitHub 页面生成

除了手写 Markdown，也可以在 GitHub 上生成：

1. 打开仓库的 `Actions` 页面。
2. 在左侧选择目标工作流。
3. 打开工作流页面右侧的菜单。
4. 选择 `Create status badge`。
5. 选择分支并复制 Markdown。

### 徽章异常时如何排查

- 显示 `failing`：点击徽章，进入最近一次失败运行，从失败的 job 和 step 查看日志。
- 显示 `no status`：检查该工作流是否在目标分支运行过，以及 `branch` 参数是否拼写正确。
- 图片加载失败：检查仓库用户名、仓库名和 workflow 文件名是否正确。
- 工作流文件改名：同步更新 README 中的图片地址和跳转地址。
- 刚运行成功但仍显示旧状态：徽章可能存在短暂缓存，稍后刷新再看。

徽章变绿只能说明对应工作流通过，不能替代代码评审、安全设计和生产环境验证。

## 5. Release 流水线：从 Tag 到可下载制品

### Tag、Artifact 和 Release 的区别

- **Git Tag**：指向某个 Git 提交的版本标记，例如 `v0.1.0`。它回答“这个版本对应哪份源码”。
- **Workflow Artifact**：某次 GitHub Actions 运行期间生成的临时文件，用于在 job 之间传递构建结果，也可以从该次运行页面下载。
- **GitHub Release**：围绕某个 Tag 创建的正式发布页面，包含发布说明和供用户长期下载的文件。
- **Checksum**：发布文件的摘要。下载者重新计算 SHA256 后，可以判断文件是否损坏或被替换。

它们之间的关系是：Tag 触发流水线，流水线产生 Artifact，最后把 Artifact 和 Checksum 发布到 GitHub Release。

### AgentForge 的发布流程

```text
创建并推送 v0.1.0 Tag
  ↓
验证 Tag 格式
  ↓
后端 test / vet + 前端 lint / test / build
  ↓
上传 React dist 作为工作流 Artifact
  ↓
并行交叉编译五个 Go 目标
  ├─ windows/amd64
  ├─ linux/amd64
  ├─ linux/arm64
  ├─ darwin/amd64
  └─ darwin/arm64
  ↓
每个平台组装完整不可变压缩包
  ↓
生成 checksums.txt
  ↓
创建 GitHub Release
```

`workflow_dispatch` 手动运行用于发布前演练：它会完成验证、构建和打包，但不会创建正式 Release。只有 `refs/tags/v...` 触发的运行才执行发布 job。

### 为什么前端需要先上传 Artifact

Release workflow 的 `web` job 只构建一次 React。构建结果通过 `upload-artifact` 保存，随后五个并行的 `package` job 使用 `download-artifact` 取得同一份前端产物。

这样可以避免前端重复构建五次，也保证每个平台压缩包包含完全相同的网站文件。

### 不可变发布包的目录约定

Linux 发布包解压后采用以下结构：

```text
release-directory/
├── api
├── migrate
├── web/dist/
└── deploy/
    ├── env/
    ├── nginx/
    └── systemd/
```

二进制必须位于根目录，因为 systemd 使用：

```text
/srv/gofiber-gorm-next/current/api
/srv/gofiber-gorm-next/current/migrate
```

如果流水线把二进制放到 `server/`，构建虽然成功，部署后 systemd 仍会因为找不到文件而启动失败。这说明“构建通过”不等于“制品可以部署”，制品布局也属于发布契约。

不可变的含义是：发布后的 `v0.1.0` 文件不在服务器上原地修改。发现问题时构建新版本，部署时通过 `current` 软链接切换版本；回滚则把软链接指回上一版本。

### 使用 linker 参数写入版本信息

Go 构建使用 `-ldflags -X` 覆盖 `buildinfo` 包中的变量：

```text
-X github.com/kael777/agentforge/backend/gofiber-gorm-next/internal/buildinfo.Version=v0.1.0
```

`-X` 后面的包路径必须与 `go.mod` 和源码 import 的正式路径一致。修改 Go module 后如果忘记同步构建脚本，二进制可能仍显示默认的 `dev` 或 `unknown`。

本地可以先指定预期版本构建，再在二进制中检查该字符串是否存在。实际运行后还可以通过 `/healthz` 查看 `version`、`commit` 和 `build_time`。

### 为什么固定 Action 的 commit SHA

Workflow 中使用完整 commit SHA，例如：

```yaml
uses: actions/setup-go@b7ad1dad31e06c5925ef5d2fc7ad053ef454303e # v7.0.0
```

注释负责告诉人类这是哪个版本，SHA 负责让 GitHub 执行确定的代码。相比只写 `@v7`，固定 SHA 可以降低标签被移动后流水线行为发生变化的风险。

升级 Action 时需要同时检查它使用的 Node 运行时、GitHub-hosted runner 支持情况和官方迁移说明，不能只机械修改版本数字。

### 校验下载文件

Linux：

```bash
sha256sum -c checksums.txt
```

Windows PowerShell 可以计算单个文件：

```powershell
Get-FileHash .\agentforge_v0.1.0_windows_amd64.zip -Algorithm SHA256
```

将结果与 `checksums.txt` 中对应文件的摘要比较。

### 正式发布前检查清单

1. 工作区干净，所有准备发布的修改已经提交并推送。
2. `AgentForge CI` 和 `Secret Scan` 都通过。
3. 手动运行一次 `AgentForge Release`，下载并检查构建 Artifact。
4. 确认压缩包根目录包含二进制、`web/dist` 和 `deploy`。
5. 确认版本信息成功写入二进制。
6. 再创建并推送 `vMAJOR.MINOR.PATCH` Tag。
7. Release 创建后验证 SHA256，并在测试环境执行部署与回滚演练。

已经发布的版本不要删除后重新使用相同 Tag；应修复问题并发布新的补丁版本。

### 后续版本如何发布

AgentForge 的版本号来自 Git Tag，不需要在 Release workflow 中手工修改版本。发布前先根据语义化版本选择新版本号：

- `v0.1.1`：修复缺陷，没有增加明显的新功能。
- `v0.2.0`：增加一批向后兼容的新功能，例如完成 Phase 1 Agent Demo。
- `v1.0.0`：项目达到第一个明确、稳定的公开接口和交付基线。
- `v2.0.0`：稳定版本之后出现重要的不兼容变更。

以发布 `v0.2.0` 为例，先确认准备发布的代码已经合并并推送到 `main`：

```powershell
cd D:\work\work\agentforge
git switch main
git pull --ff-only
git status
git log -1 --oneline
```

`git status` 必须显示 `working tree clean`。正式发布前最好同步更新 README 和 `CHANGELOG.md`，并确认 `AgentForge CI`、`Secret Scan` 已通过。

Windows 使用项目提供的 PowerShell 脚本：

```powershell
.\devops\scripts\publish.ps1 -Version v0.2.0
```

Linux、macOS 或安装了 Make 的环境可以使用：

```bash
make publish VERSION=v0.2.0
```

`publish.ps1` 会依次检查工作区、执行完整检查、创建 annotated tag，并把 Tag 推送到 GitHub。Tag 推送会触发正式 Release workflow；随后需要在 GitHub 的 `Actions → Release` 确认任务通过，并在 `Releases → v0.2.0` 检查五个平台制品和 `checksums.txt`。

如果只是 GitHub Runner 或网络等偶发问题，可以重新运行失败的 job。如果需要修改代码才能解决，就提交修复并发布新的补丁版本，例如 `v0.2.1`；不要删除并重新使用已经公开的 `v0.2.0` Tag。

## 6. 当前形成的安全与质量防线

```text
本地编辑
  ├─ .gitignore：避免提交本地环境文件和构建产物
  ├─ .gitattributes：固定跨平台文本格式
  ├─ go fmt / test / vet / build：检查后端格式、测试和编译
  └─ git diff --check：检查空白和换行问题
       ↓
GitHub
  ├─ Push Protection：尽量在敏感信息进入仓库前阻止推送
  ├─ Secret Scan / Gitleaks：扫描提交和历史
  └─ AgentForge CI：检查后端、前端和 Compose 配置
```

这些机制不能保证永远不出错，但可以把很多依赖人工记忆的检查变成自动执行的规则。
